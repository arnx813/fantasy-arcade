# Fantasy Arcade

A provably-fair crypto casino: 14 house originals including a live multiplayer Crash, a
USD-denominated wallet with crypto deposits and reviewed withdrawals, VIP rakeback,
referrals, chat, responsible-gaming controls, an operator console, and a seamless-wallet
integration point for third-party slots and live dealer content.

No dependencies. Node 22.13+ runs it as-is (built-in `node:sqlite`, `node:crypto`, a
hand-rolled WebSocket), and the browser client is plain ES modules with no build step.

```
npm start            # http://localhost:8080
npm test             # end-to-end API tests on a throwaway database
npm run sim          # Monte Carlo RTP check for every game
npm run reconcile    # ledger integrity check (exit 1 on mismatch)
npm run make-admin -- you@example.com
```

In development the payments adapter is `mock`: open the wallet and use the
"simulate a deposit" buttons. The demo slots provider is enabled too.

## Games

| Game | Type | RTP | Notes |
|---|---|---|---|
| Crash | multiplayer | 99% | Hash-chain seeded rounds, auto cash-out, bet-next-round |
| Dice | instant | 99% | 0.00–100.00 roll, over/under |
| Limbo | instant | 99% | Target up to 1,000,000× |
| Plinko | instant | 99% | 8–16 rows, three risk levels |
| Keno | instant | 99% | 40 tiles, 10 drawn, four risk levels |
| Wheel | instant | 99% | 10–50 segments, three risk levels |
| Coinflip | instant | 99% | 1.98× |
| Roulette | instant | 97.3% | Single zero, all inside and outside bets |
| Baccarat | instant | 98.9% | Standard tableau, banker 0.95:1, tie 8:1 |
| Mines | multi-step | 99% | 1–24 mines |
| Tower | multi-step | 99% | Five difficulties, nine floors |
| HiLo | multi-step | 99% | Skip, cash out any time after a win |
| Blackjack | multi-step | ~99.5% | 3:2, S17, double any two, one split, no insurance |
| Video Poker | multi-step | 99.5% | Jacks or Better 9/6 |

Plinko, Keno and Wheel payout tables are generated by `scripts/gen-tables.js`, which
shapes each curve and normalises it to the target RTP. Change a shape there and re-run
`npm run tables`; the script refuses to write a table outside 98.5–99%.

## Provable fairness

Per-player seed pairs. A bet's randomness is a stream of floats from
`HMAC-SHA256(serverSeed, "clientSeed:nonce:round")`, four bytes per float. The player
sees `sha256(serverSeed)` before betting, can set their own client seed, and rotating the
pair reveals the old server seed. Seeds cannot rotate while a multi-step game is open.

The game engines in `shared/games/` are pure functions used by both the server and the
in-browser verifier on `/fairness`, so the verifier runs the exact code that settled the
bet.

Crash uses a reverse SHA-256 chain (100,000 rounds per chain). Only the final hash is
published; each round reveals its hash, and hashing it gives the previous round's. The
crash point is `HMAC-SHA256(roundHash, salt)`, so set `CRASH_SALT` to something you commit
to publicly before the first round (a future Bitcoin block hash is the usual choice) and
never change it for an existing chain.

## Money

All amounts are integer micro-USD (1 USD = 1,000,000). Every balance change goes through
`server/services/wallet.js#adjust`, which writes one append-only ledger row with the
resulting balance, inside the same transaction as the bet or deposit that caused it.
`npm run reconcile` re-derives every balance from the ledger.

SQLite runs synchronously in-process, so transactions cannot interleave: there is no
double-spend window between checking and debiting a balance. This is a single-process
design. To scale horizontally, reimplement `server/db/index.js` (`one`, `all`, `run`,
`tx`, `afterCommit`) on Postgres with row locks, and move the Crash loop and websocket
fan-out to one leader process or a pub/sub bus.

Limits enforced on every bet: min/max bet, and max profit per bet (instant games reject
bets whose best case exceeds it; multi-step games refuse the step that would; Crash turns
it into a forced auto cash-out).

## Payments

`server/services/payments.js` has two adapters:

- `mock` for development (fake addresses, instant credit).
- `gateway`, a stub you fill in for your processor: `depositAddress(userId, chain)` and
  `sendWithdrawal(withdrawal)`, both idempotent on our ids.

Deposits arrive at `POST /api/payments/webhook`, signed with `x-signature` =
hex HMAC-SHA256 of the raw body using `PAYMENTS_WEBHOOK_SECRET`. Translate your gateway's
callback into this shape (or adapt the handler):

```json
{ "type": "deposit", "address": "...", "chain": "BTC", "asset": "BTC",
  "tx_hash": "...", "asset_amount": "0.0012", "amount_usd": 81.40, "confirmed": true }
```

Unconfirmed events record a pending deposit; the confirmed event credits it once. The
`(provider, tx_hash)` uniqueness makes retries safe.

Withdrawals debit the balance immediately and wait in the admin queue. Approve sends
through the adapter (claimed first so a double click cannot send twice); reject refunds.
Requests are refused until the player has wagered `WITHDRAW_ROLLOVER`× their deposits,
and above `KYC_THRESHOLD_USD` until an operator marks KYC verified. A KYC vendor would set
that status from its webhook.

## Third-party slots and live dealer

Content from studios comes through an aggregator's seamless wallet. We mint a launch
token per session, the aggregator calls back:

```
POST /api/aggregator/:provider/balance   { token }
POST /api/aggregator/:provider/debit     { token, tx_id, round_id, amount }
POST /api/aggregator/:provider/credit    { token, tx_id, round_id, amount }
POST /api/aggregator/:provider/rollback  { token, tx_id, original_tx_id }
```

Signed with `x-signature` = hex HMAC-SHA256 of the raw body using `AGGREGATOR_SECRET`.
Amounts are integer micro-USD. Every call is idempotent on `tx_id`; a rollback that
arrives before its debit leaves a tombstone so the late debit is refused. Most
aggregators use their own field names and decimal amounts, so expect a thin mapping
layer in `server/routes/api.js`. Fill `provider_games` from the aggregator's catalog API
and return their launch URL from `launch()` in `server/services/aggregator.js`.

The `demo` provider (six slots under `/slots`) exercises the same debit/credit path and
is disabled when `NODE_ENV=production` or `MOCK_PROVIDER=0`.

## Rewards

- VIP tiers by lifetime wager (`server/services/vip.js`), rakeback 5–15% of theoretical
  edge, claimable any time.
- Referrals: `?r=code` links; the referrer earns `AFFILIATE_SHARE` of the referee's
  theoretical edge, for life.
- Operators can credit a `bonus` from the console (audited).

## Responsible gaming and compliance hooks

- Daily (rolling 24h) loss and wager limits. Lowering applies now; raising waits 24h.
- Self-exclusion from 24 hours to permanent; blocks originals, Crash and slot launches.
- Geo-blocking by the country header your CDN sets (`COUNTRY_HEADER`,
  `BLOCKED_COUNTRIES`) on registration, betting and launches.
- KYC status per account, audit log for every operator action.

These are hooks, not a licence. Which territories to block, what KYC/AML checks apply,
and age verification rules depend on the licence you operate under; set them with your
compliance counsel.

## Security notes

- Session: random token in an HttpOnly, SameSite=Lax cookie (Secure in production), only
  its SHA-256 is stored. Passwords: scrypt.
- CSRF: JSON-only request bodies plus an Origin check on every non-GET API call.
- Strict CSP (`script-src 'self'`), no inline scripts.
- Rate limits on auth and betting (in-memory; per process).
- Mine layouts, card sequences and other hidden state stay server-side until a round ends.

```
  index.js            HTTP server, static files, websocket
  config.js           environment configuration
  db/                 schema + SQLite access (swap point for Postgres)
  lib/                http router, websocket, auth, fairness rng
  routes/api.js       every API route
  services/           bets, crash, wallet, payments, aggregator, users, rg, vip, chat, hub
shared/               game engines, payout tables, crash math (server + browser)

scripts/              table generator, admin + reconcile tools

```
